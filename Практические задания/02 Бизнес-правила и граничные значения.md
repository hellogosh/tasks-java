# Практическое задание 02. Бизнес-правила и граничные значения

## Цель

Закрепить проверки бизнес-валидации: позитивные, негативные и граничные сценарии.

## Стартовая точка

Работайте в `starter-project`. Скопируйте заготовку модуля в проект:

- `заготовки/02/ProjectCodeValidator.java` → `src/main/java/training/tracker/`

Тесты — в `src/test/java/training/tracker/ProjectCodeValidatorTest.java`.

## Исходное требование

```text
Код проекта валиден, если:
- он не null;
- его длина от 2 до 10 символов включительно;
- он состоит только из заглавных латинских букв и цифр;
- он начинается с буквы.
```

## Разминка (начало занятия, 13 минут)

Вопросы по первой встрече — устно, на слайдах. Код не пишем.

## База

Обязательные сценарии валидатора — 11: 6 на длину и 5 на допустимые символы. Параметризацию изучим на следующем занятии, поэтому сегодня один сценарий — один тестовый метод: 11 методов в `ProjectCodeValidatorTest`.

### Задание 1. Своя функция с циклом


Сколько раз вы ответили «да»? Это и есть результат метода.

### Задание 2. Покрыть длину кода проекта

В `ProjectCodeValidatorTest` должны быть тесты (`null`, `""` и `"QA"` пишем вместе на демо — самостоятельно допишите остальные три):

- `null` невалиден;
- `""` невалиден;
- `"Q"` невалиден;
- `"QA"` валиден;
- строка из 10 символов (`"PROJECT123"`) валидна;
- строка из 11 символов (`"PROJECT1234"`) невалидна.

### Задание 3. Покрыть допустимые символы

Каждый негативный тест нарушает **ровно одно** условие требования:

- `"QA1"` валиден;
- `"Qa"` невалиден — строчная буква после правильной первой;
- `"QA-1"` невалиден — дефис;
- `"Q_A"` невалиден — подчёркивание;
- `"1QA"` невалиден — начинается с цифры.

`"qa"` можно добавить дополнительным тестом, но он нарушает сразу два условия — первую букву и допустимые символы — и не заменяет `"Qa"`.

### Задание 4. Улучшить диагностику

Добавьте business-readable assertion message минимум в 3 теста. Сообщение должно называть нарушенное правило, например `"Код проекта не может начинаться с цифры"`.

### Выходная задача

Разработчик ошибся в методе `isDigit` валидатора: вместо `value >= '0'` написал `value > '0'`.

1. Не запуская тесты, запишите прогноз: какие ваши тесты упадут?
2. Внесите эту ошибку в `ProjectCodeValidator` и запустите `./gradlew test`. Совпало с прогнозом?
3. Если все тесты зелёные — какого значения в наборе не хватает? Допишите тест и убедитесь, что на коде с ошибкой он красный.
4. Верните `>=` — все тесты снова зелёные.

Подсказка: `'0'` в одинарных кавычках — символ `char`, а не число `0` и не строка `"0"`. Цифры `'0'`–`'9'` идут подряд, поэтому `value >= '0' && value <= '9'` — «символ — цифра».

## Практика+

- Добавьте тесты на границу «ровно одна цифра после буквы» (`"Q1"`) и «только цифры» (`"12"`).
- Проверьте код из 10 символов, где последний символ — цифра, и из 10 символов, где первый — цифра.
- Кириллическая буква: `"QА"`, где вторая «А» — русская. По требованию это невалидный код: разрешены только латинские буквы. Тест ценен тем, что разницу не видно глазами.
- В `ProjectCodeStats` напишите `lengthHint(String code)` через `if / else if / else`: `"слишком короткий"` для длины меньше 2, `"слишком длинный"` для длины больше 10, иначе пустая строка. Решите сами, что вернуть для `null`, и зафиксируйте решение тестом.

## Challenge

Код с пробелом по краям `" QA"`. Для валидатора ожидание однозначно — `false`: пробел не буква. Зафиксируйте это тестом. Открытый вопрос лежит за пределами валидатора: должна ли система обрезать пробелы (trim) на входе — в форме или API, до вызова валидатора? Сформулируйте этот вопрос к аналитику.

## Критерии приемки

- 11 обязательных сценариев валидатора покрыты 11 тестовыми методами, все проходят.
- Каждый негативный тест на символы и первую букву берёт непустую строку допустимой длины и нарушает только одно условие; `null` и пустая строка — особые случаи.
- Таблица трассировки `"Q2A7"` заполнена; `countDigits` дописан по заготовке или написан с нуля, к нему 4 теста, все проходят.
- Использованы `assertTrue` и `assertFalse`.
- Минимум в 3 проверках есть assertion message.
- Имена тестов описывают бизнес-поведение.
- В выходной задаче прогноз записан до запуска; ошибка `value > '0'` в `isDigit` ловится вашим тестом.
