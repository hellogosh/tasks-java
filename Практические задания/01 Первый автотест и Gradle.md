# Практическое задание 01. Первый автотест и Gradle

## Цель

Запустить проект, написать первые JUnit-тесты для простого бизнес-правила и научиться читать падение.

## Стартовая точка

Работайте в `starter-project`. Класс под тестом уже лежит в проекте:

- `src/main/java/training/tracker/SlaCalculator.java`

Тесты создавайте в `src/test/java/training/tracker/` — в том же пакете `training.tracker`.

В проекте уже есть `src/test/java/training/tracker/environment/EnvironmentSmokeTest.java` — тест проверки окружения. Его не меняйте: он показывает, что JUnit запускается на Java 25.

Если забыли синтаксис — файл `Памятка участника — опоры Java.md` в корне проекта.

## Исходное требование

```text
Система должна показывать срок реакции на задачу в часах.

Правила:
- CRITICAL: 2 часа.
- HIGH: 8 часов.
- MEDIUM: 24 часа.
- LOW: 72 часа.
- неизвестный приоритет: -1.
```

## База

### Первый тест — вместе с тренером

Создайте класс `SlaCalculatorTest` и напишите тест:

```java
package training.tracker;

import org.junit.jupiter.api.Test;

import static org.junit.jupiter.api.Assertions.assertEquals;

class SlaCalculatorTest {

    @Test
    void criticalTaskShouldHaveTwoHoursResponseTime() {
        SlaCalculator calculator = new SlaCalculator();

        int actualHours = calculator.responseTimeHours("CRITICAL");

        assertEquals(2, actualHours);
    }
}
```

Запустите его из IDE и через Gradle:

```bash
./gradlew test
```

В выводе должна быть строка `SlaCalculatorTest > criticalTaskShouldHaveTwoHoursResponseTime() PASSED`.

### Второй тест — сами

Не копируя со слайда, напишите тест: `HIGH` возвращает `8`.

### Задание 1. Дописать покрытие SLA

Добавьте тесты для правил:

- `MEDIUM` возвращает `24`;
- `LOW` возвращает `72`;
- неизвестный приоритет `BLOCKER` возвращает `-1`.

### Задание 2. Проверить регистр

Добавьте тест, который показывает текущее поведение для значения `critical`. Не исправляйте код: сначала зафиксируйте фактическое поведение тестом.

### Задание 3. Улучшить читаемость

В каждом тесте:

- понятное имя;
- подготовка, действие и проверка разделены пустыми строками;
- хотя бы в одной проверке есть сообщение, например `"CRITICAL задача должна иметь срок реакции 2 часа"`.

### Выходная задача — в конце занятия

Слайды закрыты. С нуля напишите тест: что вернёт `responseTimeHours("MEDIUM ")` с пробелом в конце? Запишите ожидание, запустите, затем сломайте ожидание и назовите соседу `expected`, `but was` и строку падения.

## Практика+

Добавьте тесты для пустой строки `""` и для `null`. Что вернет метод? Почему он не падает на `null`?

## Challenge

Временно поменяйте ожидание в одном тесте на неверное, запустите `./gradlew test` и найдите в выводе: `expected`, `but was` и строку вашего теста. Затем верните правильное значение.

## Команды проверки

```bash
./gradlew test
```

## Критерии приемки

- Покрыты 6 сценариев требования: `CRITICAL`, `HIGH`, `MEDIUM`, `LOW`, неизвестный `BLOCKER`, нижний регистр `critical`. Один сценарий — один тестовый метод, итого 6 методов, все проходят.
- 5 из 6 методов написаны самостоятельно, без копирования со слайда (`CRITICAL` пишется вместе с тренером).
- У каждого теста понятное имя.
- В одном из тестов есть assertion message.
- `./gradlew test` завершается `BUILD SUCCESSFUL`, и в выводе видны `PASSED` для ваших тестов, а не только для `EnvironmentSmokeTest`.
