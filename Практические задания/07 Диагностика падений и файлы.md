# Практическое задание 07. Файлы и диагностика падений

## Цель

Проверять исключения через `assertThrows()`, читать тестовые данные из файла и разбирать падения по stack trace.

## Стартовая точка

Работайте в `starter-project`. Скопируйте заготовки модуля в `src/main/java/training/tracker/`:

- `заготовки/07/TaskWorkflow.java`
- `заготовки/07/TaskFileReader.java`
- `заготовки/07/TaskLineParser.java`

Если `Task` на enum или `TaskBuilder` из модуля 6 не доделаны — сначала возьмите комплект из `заготовки/06-если-не-успели` и пройдите порядок из раздела «Если модуль 6 не закончен» карточки 06: модели и `TaskService` — в `src/main/java/training/tracker/`, builder — в `src/test/java/training/tracker/builders/`, тесты модуля 5 переводятся без удаления проверок.

Заготовки рассчитаны на `Task` с `TaskStatus` и `Priority` из модуля 6. Файл данных уже лежит в `src/test/resources/tasks.txt`:

```text
QA-1;Write tests;OPEN;HIGH
QA-2;Fix bug;DONE;MEDIUM
QA-3;Review checks;OPEN;LOW
```

## Исходное требование

```text
Задачу можно закрыть, если у нее заполнен заголовок.
Если заголовок null, пустой или состоит только из пробельных символов, система должна выбросить IllegalArgumentException.
Сообщение: "Task title is required".
```

Формат `tasks.txt` — учебный, с разделителем `;`, а не полноценный CSV: кавычки, переносы строк и `;` внутри заголовка не поддерживаются.

## Разминка

Вопросы по прошлой встрече, без кода: обсуждаем вместе на занятии. Затем скопируйте заготовки из раздела «Стартовая точка» и запустите `./gradlew test`.

## База

### Задание 1. Прочитать файл и проверить закрытие задачи

Сначала напишите `TaskFileReaderTest`: прочитайте `tasks.txt` через `TaskFileReader.readLines(Path)` и проверьте, что в файле ровно 3 строки и первая — `QA-1;Write tests;OPEN;HIGH`. После имени тестового метода допишите `throws Exception`, иначе не скомпилируется. Путь к ресурсу получайте через `getResource()`, а если он вернул `null` — бросайте `IllegalStateException("Test resource not found: " + fileName)`, чтобы опечатка в имени файла давала понятное сообщение.

Затем `TaskWorkflowTest`, задачи создавайте через `TaskBuilder`:

- задача с заголовком закрывается — статус `DONE`;
- заголовок `null` — не закрывается;
- заголовок `""` (пустая строка) — не закрывается;
- заголовок `" "` (пробельная строка) и `"\t"` — не закрывается (удобно `@ParameterizedTest` + `@ValueSource(strings = {"", " ", "\t"})`).

### Мини-задача. Свой `throw`

Добавьте в `TaskWorkflow` метод `start(Task task)`: задача `OPEN` переходит в `IN_PROGRESS`, в другом статусе — `IllegalStateException("Only OPEN task can be started")`. Успешный тест — сразу, в `TaskWorkflowTest`; негативный — когда разберем `assertThrows`.

### Задание 2. Проверить сообщение исключения

Для негативных сценариев проверьте тип исключения и текст `"Task title is required"`:

```java
IllegalArgumentException exception = assertThrows(
        IllegalArgumentException.class,
        () -> workflow.close(task)
);
```

Тип и сообщение подтверждают способ отказа и его причину. Если важно, что состояние не изменилось, это проверяется отдельно.

### Задание 3. Разобрать падение

Тренер выдает тест с ошибкой — один из четырех: `BrokenTitleTest`, `BrokenExceptionTypeTest`, `BrokenResourceTest`, `BrokenStatusTest`. Положите его в `src/test/java/training/tracker/`, запустите в IDE и разберите по алгоритму (полный stack trace — в окне Run или в `build/reports/tests/test/index.html`, терминал показывает только тип и строку): тип и сообщение → место возникновения (первая строка пакета `training.tracker`) → место вызова (строка теста) → цепочка `Caused by`, если есть. Отличите упавшую проверку (`AssertionFailedError`) от исключения (`NullPointerException`, `IllegalArgumentException`) и решите, где ошибка: в тесте, в данных или в коде. Исправьте.

### Задание 4. Разобрать строку файла

Напишите `TaskLineParserTest`:

- `"QA-1;Write tests;OPEN;HIGH"` превращается в `new Task("QA-1", "Write tests", TaskStatus.OPEN, Priority.HIGH)` — сравнение целиком;
- 3 поля (`"QA-1;Write tests;OPEN"`) — `IllegalArgumentException` с сообщением `"Task line must have 4 fields, but got 3: QA-1;Write tests;OPEN"`;
- три строки с лишним полем — 5 полей (`"QA-1;Write tests;OPEN;HIGH;extra"`), завершающая `;` (`"QA-1;Write tests;OPEN;HIGH;"`) и лишняя `;` в середине (`"QA-1;Write tests;;OPEN;HIGH"`) — `IllegalArgumentException`, сообщение начинается с `"Task line must have 4 fields"`. Удобно одним `@ParameterizedTest` с `@ValueSource`.

Готово, когда в `TaskLineParserTest` 3 метода и все зелёные: 5 запусков.

Почему парсер использует `split(";", -1)`: без `-1` Java отбрасывает пустые поля в конце, и строка с лишним `;` прошла бы как правильная.

### Задание 5. Файл → задачи → фильтр

Один тест на весь путь данных: прочитайте `tasks.txt`, в цикле разберите каждую строку через `TaskLineParser`, отфильтруйте задачи `OPEN` через `TaskService.tasksWithStatus()` и проверьте **состав** результата — ключи `QA-1` и `QA-3`, а не только их количество.

Тест пишите в том же классе `TaskFileReaderTest`: там уже есть `resourcePath()`, а он объявлен `private` — в другом классе будет ошибка `cannot find symbol`. Ключи задач из списка: `openTasks.stream().map(task -> task.key()).toList()`. Готово, когда в `TaskFileReaderTest` 2 зелёных теста — чтение файла и этот — и вы можете сказать, что новый тест подтверждает, а что нет.

## Практика+

Для тех, кто закончил задание 5 раньше времени.

- Пустой файл: создайте пустой `src/test/resources/tasks-empty.txt`. Тест: `readLines()` возвращает **пустой** список, а не `null` и не исключение.
- Пустой приоритет (`"QA-1;Write tests;OPEN;"`) — `IllegalArgumentException` про неверное значение (`No enum constant`), а не про число полей.
- Что произойдет со строкой `QA-4;Write docs;UNKNOWN;HIGH`? Зафиксируйте поведение тестом.
- Попросите соседа незаметно сломать одно место в вашем проекте и разберите падение по алгоритму.

## Challenge

Добавьте в `src/test/resources` файл с ошибочной строкой и напишите тест, который показывает, **какая именно** строка файла сломана (номер строки в сообщении).

## Команды проверки

```bash
./gradlew test
```

## Критерии приемки

- Минимум 3 теста с `assertThrows()`, отдельно `null`, `""` и пробельные строки.
- Проверено сообщение исключения.
- Написан и проверен свой метод с `throw`.
- Разобран stack trace упавшего теста.
- Тестовые данные прочитаны из resource-файла, отсутствующий ресурс дает понятное сообщение.
- Парсер проверен на 3, 4 и 5 полях и завершающем `;`.
- Тест «файл → задачи → фильтр» проверяет состав результата.
- Все тесты проходят через `./gradlew test`.
